# Database

**File:** `database/schema.sql` (reference DDL; in normal dev usage Hibernate's `ddl-auto: update` creates/updates these same tables automatically from the `@Entity` classes at startup — see `application.yml`).

Engine: **PostgreSQL 16**. Database name defaults to `task_manager` (must be created manually first — PostgreSQL, unlike MySQL, has no "create if not exists from a connection string").

## Table: `users`

| Column | Type | Constraints | Notes |
|---|---|---|---|
| `id` | `BIGINT` (identity) | `PRIMARY KEY` | Auto-generated (`GENERATED BY DEFAULT AS IDENTITY`) |
| `name` | `VARCHAR(100)` | `NOT NULL` | Display name |
| `email` | `VARCHAR(150)` | `NOT NULL`, `UNIQUE` (`uk_users_email`) | Also used as the Spring Security "username" |
| `password` | `VARCHAR(255)` | `NOT NULL` | BCrypt hash — never the plaintext password |
| `role` | `VARCHAR(20)` | `NOT NULL DEFAULT 'ROLE_USER'` | `ROLE_USER` or `ROLE_ADMIN` (stored as enum name string) |
| `created_at` | `TIMESTAMP(6) WITH TIME ZONE` | `NOT NULL` | Set automatically by JPA auditing (`@CreatedDate`) |

Maps to the `User` JPA entity (`backend/.../user/User.java`), which also implements Spring Security's `UserDetails` interface directly — there's no separate "principal" class.

## Table: `tasks`

| Column | Type | Constraints | Notes |
|---|---|---|---|
| `id` | `BIGINT` (identity) | `PRIMARY KEY` | Auto-generated |
| `title` | `VARCHAR(150)` | `NOT NULL` | |
| `description` | `TEXT` | nullable | Free text, up to 5000 chars enforced at the DTO validation layer |
| `priority` | `VARCHAR(20)` | `NOT NULL DEFAULT 'MEDIUM'` | Enum: `LOW \| MEDIUM \| HIGH` |
| `status` | `VARCHAR(20)` | `NOT NULL DEFAULT 'TODO'` | Enum: `TODO \| IN_PROGRESS \| DONE` |
| `due_date` | `DATE` | nullable | No time component, just a calendar date |
| `user_id` | `BIGINT` | `NOT NULL`, `FOREIGN KEY → users(id) ON DELETE CASCADE` | Owner of the task |
| `created_at` | `TIMESTAMP(6) WITH TIME ZONE` | `NOT NULL` | Set by `@CreatedDate` on first save |
| `updated_at` | `TIMESTAMP(6) WITH TIME ZONE` | `NOT NULL` | Refreshed by `@LastModifiedDate` on every save |

Maps to the `Task` JPA entity (`backend/.../task/Task.java`).

### Indexes on `tasks`

| Index | Column | Purpose |
|---|---|---|
| `idx_tasks_user` | `user_id` | Every task query is scoped to the owning user — this is the most important index |
| `idx_tasks_status` | `status` | Supports the `status` filter in `GET /tasks` |
| `idx_tasks_priority` | `priority` | Supports the `priority` filter |
| `idx_tasks_due_date` | `due_date` | Supports sorting by `dueDate` |

These indexes are declared both in `schema.sql` and redundantly on the `Task` entity itself via `@Table(indexes = {...})`, so they're created either way (manual script or Hibernate auto-DDL).

## Relationship

```
users (1) ──────< (many) tasks
        id            user_id (FK, ON DELETE CASCADE)
```

One user has many tasks. Deleting a user cascades to delete all of their tasks at the database level (`ON DELETE CASCADE`). On the JPA side this is a `@ManyToOne(fetch = FetchType.LAZY, optional = false)` from `Task` to `User` — the relationship is unidirectional (there's no `List<Task>` collection on `User`); every task lookup goes through `TaskRepository`, not through navigating `user.getTasks()`.

## How Hibernate maps enums

`Priority` and `TaskStatus` are plain Java enums (`LOW/MEDIUM/HIGH`, `TODO/IN_PROGRESS/DONE`). Both are persisted with `@Enumerated(EnumType.STRING)`, so the database stores the readable string (`'HIGH'`, `'IN_PROGRESS'`) rather than an ordinal integer — this is what makes the `VARCHAR(20)` columns line up with the schema file.

## Auditing timestamps

`@EnableJpaAuditing` is turned on in `TaskManagerApplication`. Combined with `@EntityListeners(AuditingEntityListener.class)` on both entities, this makes `@CreatedDate`/`@LastModifiedDate` fields self-populating — no code anywhere sets `createdAt`/`updatedAt` manually.

## Schema provisioning: two modes

1. **Development (default):** `application.yml` sets `spring.jpa.hibernate.ddl-auto: update`. Hibernate inspects the `@Entity` classes on startup and creates/alters tables to match. `database/schema.sql` is not actually executed in this mode — it exists purely as human-readable documentation of what Hibernate will produce.
2. **Production (recommended per the README):** switch `ddl-auto` to `validate` and provision the schema explicitly by running `psql -U postgres -d task_manager -f database/schema.sql` — Hibernate then only checks the existing schema matches the entities, rather than mutating it.
